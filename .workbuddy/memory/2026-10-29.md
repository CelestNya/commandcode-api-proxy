## dsh（DeepSeek-Harness）模型请求全挂：bili 僵尸进程占端口

用户报 dsh 又坏、怀疑 billion-context 插件。排查路径与结论：

- dsh = DeepSeek-Harness 桌面端（`D:/Program/DeepSeek-Harness`，用户数据在
  `~/.dsh`，插件 pnpm 工作区在 `~/.dsh/profiles/desktop`，补丁层
  `cordis.patch.yml`）。LLM provider "cmd" 指向 `http://127.0.0.1:8787/v1`
  = 我们的 ccproxy，请求链：dsh → billion-context 压缩代理（18788）→ ccproxy → 上游
- billion-context@0.1.208 的 server 由 dsh 拉起：`node .../billion-context/dist/index.js start --host 127.0.0.1 --port 18788`
- **根因**：bili server（09:32 由上一代 dsh 拉起）僵死——netstat 显示
  LISTEN 但 connect 被拒、CPU 空转到 1 小时。用户 12:38 重启 dsh 后新实例
  起不来 bili（18788 被孤儿占着），全部模型请求失败
- **修复**：kill 孤儿 pid → 计划任务同参重启 bili（新 pid 135400，root=200、
  无鉴权请求返回 forbidden 属正常鉴权门）→ ccproxy 8787 全程 200 无辜
- **排查陷阱**：WorkBuddy 会话 shell 挂着 `http_proxy=127.0.0.1:57242`，
  curl 本机端口全被它代理并回 502 "upstream connect failed"，必须
  `--noproxy '*'` 才是真实连通性——上次 ccproxy 交接排查里的 502 假象同理
- **注意**：现在跑的 bili 是我手动拉起的孤儿（无父进程监督）。dsh 下次重启
  会自己 spawn bili，若 EADDRINUSE 冲突需先 kill 手动实例

## bili 反复僵死的根因分析

状态目录在 `~/.local/state/billion-context/`（bili.log / bili.log.old /
session-order.json 6MB / prefix-affinity.json 758KB，均每秒级重写）。

僵死签名（bili.log.old，10-29 11:08 本地=03:08Z 戛然而止）：
- 最后一行停在 turn 中间（"output budget restored"），之后 1.5h 零日志
- CPU 单核 100% 空转；netstat LISTEN 但 connect refused = 内核 backlog 塞满、
  事件循环再没回来 → **同步无限循环卡在请求处理里**，进程不死所以无人重启

驱动负载：用户的 dsh 会话 session-4aa98c48（deepseek-v4.1-flash → ccproxy
8787）当天从 5675 涨到 6191 msgs / 37.1MiB 原始历史，每个 turn 全量重发，
bili 每次都要 JSON.parse 37MiB + fold/reconcile + 重写多 MB 状态 JSON，
单 turn 本地处理已 1.1~1.2s。会话越长成本越高，涨到某点即触发死循环。
另外 bili↔ccproxy 之间 ECONNRESET 频发（age 2-12s），retry 风暴放大 CPU。

结论：bili 单线程 Node + 每 turn 同步重活 + 无限增长的单会话 = 僵死是结构性
风险；建议最大杠杆是新开会话别把单会话养到 6k+ msgs，其余上报上游（其日志
自述"reproducible 时带 bili.log 查 /acp-cache"）。插件版本 0.1.208。
