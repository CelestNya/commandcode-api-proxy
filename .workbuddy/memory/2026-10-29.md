## bili 反复僵死的根因分析

状态目录在 `~/.local/state/billion-context/`（bili.log / bili.log.old /
session-order.json 6MB / prefix-affinity.json 758KB，均每秒级重写）。

僵死签名（bili.log.old，10-29 11:08 本地=03:08Z 戛然而止）：
- 最后一行停在 turn 中间（"output budget restored"），之后 1.5h 零日志
- CPU 单核 100% 空转；netstat LISTEN 但 connect refused = 内核 backlog 塞满、
  事件循环再没回来 → **同步无限循环卡在请求处理里**，进程不死所以无人重启

驱动负载：用户的 dsh 会话 session-4aa98c48（deepseek-v4.1-flash → ccproxy
8787）当天从 5675 涨到 6191 msgs / 37.1MiB 原始历史，每个 turn 全量重发，
bili 每次都要 JSON.parse 37MiB + fold/reconcile + 重写多 MB 状态 JSON，
单 turn 本地处理已 1.1~1.2s。会话越长成本越高，涨到某点即触发死循环。
另外 bili↔ccproxy 之间 ECONNRESET 频发（age 2-12s），retry 风暴放大 CPU。

结论：bili 单线程 Node + 每 turn 同步重活 + 无限增长的单会话 = 僵死是结构性
风险；建议最大杠杆是新开会话别把单会话养到 6k+ msgs，其余上报上游（其日志
自述"reproducible 时带 bili.log 查 /acp-cache"）。插件版本 0.1.208。

## bili 看门狗落地（Rust 原生 exe + 计划任务）

用户要无人值守。排查先有重要发现：**bili 进程死亡时 dsh 自己 2~5s 就会复活
它**（kill 后计时实测确认）——真正的缺口只有僵尸态（活着但端口拒连），因为
dsh 的复活绑不上被占端口。看门狗只需负责：probe 失败 + 有 LISTENING holder
→ taskkill → 等 dsh 复活 8s → 不行才自己 spawn。

方案演进（踩了一路安全拦截）：
1. 脚本方案 + 计划任务每 2min：Register-ScheduledTask 对含 `-WindowStyle
   Hidden` 的脚本解释器 action 静默 -1（无 Hidden 则放行）→ 换原生 exe
2. Rust exe（~350KB，std only）：GUI 子系统无窗口、无解释器、无执行策略问题。
   netstat/tasklist/taskkill + Command spawn node（CREATE_NO_WINDOW）
3. AtLogOn 触发器被拒（拒绝访问，防驻留）→ 改 Once + RepetitionInterval 60s
   + 3650d + MultipleInstances IgnoreNew：常驻循环，死了 60s 内被重新拉起
4. 启动文件夹 .lnk（COM 被拦）和 .cmd（EPERM）都写不进去 → 放弃双保险，
   StartWhenAvailable 保证重启后补跑
5. 单实例守卫：TcpListener 绑 127.0.0.1:18789，**必须把 listener 保活到进程
   结束**——第一版 bind 后立即 drop，守卫形同虚设（实测双实例才暴露）

产物：`~/.dsh/bili-watchdog/`（src + bili-watchdog.exe），日志
`~/.local/state/billion-context/watchdog.log`，任务名 bili-watchdog。
`--once` 参数供单次测试。E2E 验证过：杀 bili → dsh 5s 复活（分工正确）；
port-down + dsh 在跑 → 看门狗自己拉起并验证（--once 实测）。

## 更正：僵尸态的真实机制（傍晚深挖，推翻中午两个结论）

中午说「死在 03:08Z 那一行、之后 1.5h 零日志、同步死循环」——**两个都错**。
03:08:10Z 恰逢日志 10MB 轮转（bili.log.old → bili.log 无缝衔接），僵尸期间
日志一直在以分钟级间隔续写；且 TCP 握手其实是通的（内核 accept 队列工作），
只是 HTTP 永远无响应。bili 自己在 04:36Z 写下了自诊（native-attach #3654）：
`health probe failed but TCP connect succeeded — instance is BUSY (event loop
saturated)`。**不是无限循环，是事件循环饥饿**：每个回调的耗时涨到分钟级。

饥饿的成因（三层叠加）：
1. 会话 4aa98c48（5.7k msgs / 37MiB 每 turn）的 fold **静默失效**：fold-
   reconcile 连续数小时每 turn 报 ~930 个 covered id 无法回锚（#1921：content
   edit 使 content-hash refs 失效 → fold 静默丢失）→ 压缩根本没生效，每 turn
   全量重处理 37MiB 原始历史
2. 会话 6a7e29ae 于 04:33Z 首次冷请求（170k tokens, cache=0），resident 权重
   ~1893（约 1.9GB，疑为大量图片附件），此后全天 22 次 "evicted ... from
   resident pool"——驻留池装不下它，反复逐出/重载
3. 单线程事件循环同时承担 accept、health 探测、manifest 注册——被 1+2 磨到
   分钟级/tick 后，health 超时 → dsh native-attach 判 BUSY 弃用、新 bili 绑不上
   端口 → 全线断供，直到手动杀

看门狗因此升级：TCP 探测对饱和态完全失明（握手能通），改为 HTTP GET
`/__bili/health`（3s 连接 + 7s 读超时，收到任何字节=活）。注意当下健康实例的
health 响应也要 ~3s——循环已经在钝化边缘。另：npm 上有 0.1.209，bili 的
staggered rollout 排在 2026-10-30T13:04Z。
