- WebUI 首包慢根因（2026-10-21 定位）：/api/stats 与 /api/attempts 每请求都调 Pricing::load()，pricing.json 超 24h 即在请求线程内同步抓取 commandcode.ai 价格页，FETCH_TIMEOUT=12s；本机到该主机 TLS 握手就要 ~12s，冷请求实测 11.86s、热 0.45s。加重因素：无进程内缓存（每请求读盘解析 12.7KB/94 模型）、attempts 视图双请求并发抓取无互斥、抓取失败时旧 fetchedAt 被写回导致不可达时每请求都付 12s。代理热路径不碰 pricing。修复方向：OnceLock<RwLock<Arc<Pricing>>> + stale-while-revalidate 后台刷新 + 超时降到 3s。
- 首包慢修复完成（2026-10-21，stale-while-revalidate）：pricing.rs 新增进程内表 TABLE(OnceLock<RwLock<Arc<Pricing>>>) + SEEDED(AtomicBool，swap 一次性读盘种子；选 AtomicBool 而非 OnceLock 是为了测试可重置) + LAST_ATTEMPT(Mutex<Option<Instant>>，RETRY_EVERY=60s 限流，不可达时最多每 60s 一次后台抓取)；`pricing_table(dir)` 为唯一入口，委托 `pricing_table_with(dir, fetch)`（fn 指针注入，测试零网络覆盖 spawn→写盘→换内存全链路）；删了已无调用方的 `Pricing::load`；webui.rs stats_json/attempts_json 两处切换到 pricing_table。**FETCH_TIMEOUT 保持 12s 不降**：非阻塞后长超时无害，且实测本机经系统代理抓取整页就要 ~11s（代理活着时），降到 3s 会令刷新永远失败。测试基建：tests 模块内 PRICING_TEST_LOCK(Mutex) 串行 + reset_pricing_state_for_tests() 重置三个全局态；刷新测试用 3s 慢 fetch 注入实证"首调 <1.5s 不阻塞 + 8s 内落盘 + 内存换表后 price() 可见"。
- 实测结论（开发实例 18923 + CC_DATA_DIR 隔离 + 老化 48h pricing.json）：冷请求 11.48s → **0.59s**，API 当场返回旧表（94 模型完整）；后台刷新经恢复的系统代理落地：磁盘 fetchedAt 33s 新、内存换表后 API meta 同步刷新。230 lib 测试全绿 + clippy 干净（仅 Windows 增量锁文件噪音）。
- 环境备注：本机 HTTP(S)_PROXY=127.0.0.1:64256（VPN 客户端）会间歇性死亡；死亡时 ureq 走 env 代理必失败，直连该价格页正文 >90s 下不完（12s 超时正常失败），此时刷新静默失败并按 60s 限流重试，自愈（本次会话代理死亡~10min 后恢复即验证）。**托盘实例（8787）仍跑旧二进制，需重启才生效**。ureq 2.12 无 NO_PROXY 支持且全局 agent 代理首次使用时固化——本地 fixture 的提交测试不可靠，故测试走 fn 注入而非起本地 HTTP 服务。
