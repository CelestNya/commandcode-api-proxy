# 2026-10-27 cc-proxy 生产实例 413 诊断

## 上游真实硬顶 = 32 MB（字节数，非 token）
- `api.commandcode.ai` 对单请求 body 的硬上限是 **33,554,432 字节（32 MiB）**。
- 双重确认：① 旁路实例(端口8799)实测，30MB→200、32MB→上游413；② 生产 `service/logs/dumps/` 转储的 9 个上游413，原文 "Request body is 32.0 MB, over the 32 MB limit ... Images resent with the conversation history are usually most of it"。
- 上游按字节上限，不是上下文窗口；图片/大上下文烧的是 token，不是字节上限。

## 代理默认限 vs 上游
- 代理默认 `max_body_bytes = 10 MB`（`config.rs` `MAX_BODY_BYTES_DEFAULT`），部署 `ccproxy.json` 原本没有该字段 → 走默认 → 请求>10MB 被代理本地 413（"Request body too large"）。
- 已把部署 `ccproxy.json` 加上 `"maxBodyBytes": 33554432`（对齐上游32MB，**待重启生效**）。JSON 键名是 camelCase `maxBodyBytes`。
- ⚠️ 代码坑：`MAX_BODY_BYTES_MAX = 50 MB` 高于上游真实 32MB，谁设到 50MB 会收到莫名上游413。建议降到 32MB。

## 膨胀根因（客户端 dsh，非代理）
- dump 首条 user 消息即内嵌 **3.15MB 全分辨率 base64 PNG 截图**（未降采样）。
- dsh 每回合重发整段对话历史（含所有历史截图、工具结果）；max mode 不裁剪 → 体积随会话线性增长，跨过10MB再跨过32MB。
- 翻译层 `openai.rs:224` / `anthropic.rs:317` 只透传 base64，**不做图片压缩**。
- 日志见两种画像：会话A(46个工具+133k缓存token)、会话B(0工具但历史堆截图)。均有重试风暴（同请求秒级重发，纯浪费）。

## 修复路径
- 代理侧：把 maxBodyBytes 提到 32MB 只去掉"代理早于上游拦截"这层，不能消除 >32MB 的上游413。
- 治本：客户端 `/compact` 压缩历史；或代理侧加图片降采样/重编码（翻译层新功能，需写代码+重编）。

## 同分辨率图片重编码实测（2026-10-27，合成2560x1440 IDE截图样张）
- 带噪样张(贴近真实截屏)：PNG 2.65MB → JPEG q85 481KB(5.5x) / q75 320KB(8.3x) / WebP q80 173KB(15.4x)。
- 扁平无噪样张：PNG 本身只有 0.30MB，JPEG 反而可能更大(0.9x) → **必须加 only-if-smaller 守卫**。
- 请求体 gzip(Content-Encoding)：仅 1.3x，PNG+base64 已高熵，方案否决。
- 方案设计要点：确定性编码(保缓存前缀)、SHA-256 LRU 备忘录(省CPU)、阈值跳小图、alpha 平铺白底、media_type 同步改、只重编 PNG 类。副作用：启用瞬间对旧会话有一次性缓存重建；token 计费按像素面积不变(只救字节不救token)。
- 代码接入点：openai.rs:224-231 与 anthropic.rs:317-329 两条翻译路径都汇聚到 `data:{media};base64,` 字符串构造 → 单一 hook 函数即可。

- **设计缺陷修正**：body 守卫在翻译前检查原始请求 → 17.66MB 截图请求在压缩运行前就被本地 413。修法：`image_compress.enabled` 时入站守卫抬到 `MAX_BODY_BYTES_MAX`（压缩只减不增，出站仍受上游 32MB 约束），config.rs 装配处 `.max()`，有测试钉死。

- release 二进制已构建：`target/release/ccproxy.exe`（3.5MB）。测试 234 lib 全过、clippy 0 error（warning 均为增量编译锁文件清理噪音）。

## 热接管实测 + 自启动同步修复（v0.7.2）
- **热接管协议本身完美**：0.7.0 托盘对 0.6.9 现任实测交接 ~1.3s（Standby→取得锁→启动→/health 确认→Commit→现任退出），日志齐全，/health 返回 version 0.7.0，11MB 请求过 32MB 校验到 401（旧版 10MB 会本地 413）。
- **坑1（重要）：沙箱内 Start-Process 启动的托盘会被沙箱 Job 收割**——静默死亡（无退出日志），KillOnClose Job 连带杀 ccproxy，生产曾短暂下线。**必须经 `explorer.exe <exe路径>` 在宿主上下文启动**，跨工具调用存活验证过。
- **坑2：探测宿主回环端口**——Git Bash 的 curl 被 shell env 代理（沙箱 65179）劫持回 502"upstream connect failed"（该文案不在任何版本源码里，是沙箱代理的报错！）；curl --noproxy 直连 000；**用 PowerShell 工具 Invoke-WebRequest 才能真正打到宿主 8787**（/health 200 验证可用）。
- **真 bug（已修，commit 17c99a6）**：自启动 Run 项只在用户手动 toggle 时写入 → 无缝更新后仍指旧目录，**重启电脑滚回旧版**。修法：托盘取得所有权后 `sync_autostart`——自启动开着且注册的是别处 CCProxyTray.exe 就改写到当前 exe；非托盘命令（用户自定义 wrapper）不动；命名空间实例不碰生产注册表。REG_SZ 解码（UTF-16LE 截断容忍）+ is_tray_command 纯函数各带测试（tray 52 测试全过）。
- 版本 0.7.2（fix patch）。教训：交接成功≠更新完成，**自启动路径是热接管的第四个同步点**（端口、锁、服务、自启动）。
