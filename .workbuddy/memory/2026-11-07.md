## 日志页滚动卡死（已修，66346ff）
- **根因**：`.logpane` 是 `white-space: pre`、`.ln` 是 `display:block`，但 `logs.js` 两处渲染都用 `join("\n")` 拼行。`trimLogDom` 只按 `childElementCount` 裁元素（`removeChild(firstElementChild)`），每删一个 span 就留下一个孤立的 `"\n"` 文本节点，永远清不掉。在 `pre` 下每个文本节点排成一个空行。
- **实测（4.4 MB 日志，与生产同规模）**：修前 2000 元素 + **37,240 个文本节点**，`scrollHeight` 784,824px（39,241 行，真实内容 2000 行），滚动条长度本身就是假的；主线程长任务 13 次、最长 **11,026 ms**。修后文本节点 0、`scrollHeight` 40,024px（=2000×20）、长任务 0 次、上滚/下滚每档 260px 稳定。
- **顺带**：`since=0` 以前走增量路径（每 700ms 灌 256 KiB，4 MB 日志要连追 15 轮才开始实时）。`log_increment` 现在把冷客户端和「since 越界（轮转）」合到同一条 tail 分支：给尾部 500 行 + `len=文件长度`，打开即追平。新增 `wants_tail(since, len)`。
- **守门**：`webui_site::log_lines_are_joined_without_text_separators` 钉两处必须 `join("")`（先 `strip_comments` + `flat` 再断言）；负向验证过：改回 `join("\n")` 红、改成 `join("|")` 红。
- **探针**：`.probe/log-check.js`（DOM 计数 + scrollHeight/行高比对 + 真实滚轮序列 + longtask 观察）、`.probe/log-append.js`（追加 2500 行验证 trim 与「用户上滚时不被抢」）。日志用 `CC_LOG_DIR` 指到 `.probe/logs`，复制生产 proxy.log 复现规模。
- 已知未处理（既有设计代价，用户未报）：用户停在中间时新行 append + 顶部 trim 会让眼前内容向上漂移，没做滚动补偿。
