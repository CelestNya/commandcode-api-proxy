# 断点续写（B 方案）备忘

> 状态：**未采纳**，留档备查。当前采用 A 方案（原地续接整轮重试）。
> 触发背景：2026-09-15 生产事故 —— CC 在流中途报 in-band error，旧闸门拒绝重试，
> 整轮报废。相关实现与决策见本文末「现状」。

## 1. 两个方案在做什么

用户问的「中途接续意思是代理把两个请求的输出接起来吗」——是，但要区分接的是什么：

| | A 方案（已采纳） | B 方案（本备忘） |
| --- | --- | --- |
| 上游请求 | 重发**同一个**请求（同 threadId） | 重发请求，并**带上已生成的内容**做前缀 |
| 下游拼接 | 代理抑制重复记录，把第二轮输出接在已发出的流上 | 同左，但第二轮本身是从断点开始的 |
| 上游工作量 | 整个回答重算一遍 | 只算剩下的部分 |
| 用户看到 | 一份完整回答 | 一份完整回答 |

两者的**下游行为完全相同**（都是原地续接、抑制重放），差别只在上游侧：B 让 CC
从断点继续生成，而不是从头重来。

## 2. B 方案为什么看起来更优

- **省 token**：A 方案重试时，第一次生成的全部内容（含 reasoning）都白烧了。
  生产样本里那次事故已经烧掉 7662 字符 reasoning，重试再烧一遍。
- **省时间**：重试要等上游重新生成整个回答，B 只需要生成剩下的。
- **计费更干净**：A 的第一次尝试在 CC 侧已经计费（且用量未知），B 同样计费 ——
  但 B 至少不会让"重试"变成"再买一遍"。

## 3. 为什么没有采纳

### 3.1 CC 的协议不支持「续写」

这是决定性的。CC 的 `/alpha/generate` 拿的是 `messages` 数组，不是 `completion`
前缀。要表达"从断点继续"，唯一办法是把已经生成的内容塞进 `messages`：

```jsonc
{
  "messages": [
    { "role": "user", "content": "原问题" },
    { "role": "assistant", "content": "已经生成的那半截" }
  ]
}
```

这是**换了一个语义完全不同的请求**，不是续写：

- CC/模型看到的是一个"多轮对话中的续接"，不是"同一个回答的剩余部分"。模型会
  重新审视前半截，可能修正、可能重复、可能换思路。
- 工具调用尤其危险：半截的 `tool_use` 不是合法的 assistant turn，塞回去要么被
  拒、要么让模型把工具调用重新发一遍（下游就出现了两个 tool_use，正是我们极力
  避免的）。
- thinking 块无法这样传：Anthropic 要求带 signature，我们的 placeholder 不是真的。

### 3.2 省下的 token 换来了不可预测性

A 方案的"浪费"是确定的：多烧一轮 token，回答质量不变。
B 方案的"节省"要用"可能改变模型行为"来换 —— 在一个**已经出错**的路径上，让行为
更难预测是反向优化。降级路径应当越笨越好。

### 3.3 计费上并没有实质优势

用户的硬要求是「计费不能隐瞒」。B 方案同样产生两次真实计费，同样存在第二次尝试
的用量未知问题（CC 只在 `finish` 事件回报）。它不能解决计费问题，只能减少浪费。

### 3.4 实现成本与收益不成比例

需要：识别可续写的断点类型（正文/工具/reasoning 各自不同）、把半截内容装配成合法
的 assistant turn、处理 CC 的拒绝与回退、为两个方言各写一套。而 A 方案的核心逻辑
已经只有「抑制重放 + 复用编码器」约 30 行。

## 4. 什么情况下值得回头做 B

若出现以下信号，可以重新评估：

1. 计费数据显示**重试导致的重复消耗**成为实际成本问题（需要台账先跑一段时间，
   统计 `status='interrupted'` 之后紧跟 `status='ok'` 的成对记录占比）。
2. 长回答场景（>30s 生成）中，重试等待时间成为用户可感知的痛点。
3. CC 未来提供真正的续写 API（如支持 `completion` 前缀或 continuation 语义）——
   那时 B 的语义问题消失，只剩实现成本。

## 5. 与 A 方案的接口边界（为将来留门）

A 方案的实现顺序是：**先决定拼接方式，再发请求**。

- `encoder.beginContinuation()` 表示"下一段是接续"，负责抑制重放；
- `retryStream()` 负责发出上游请求。

B 方案只需替换 `retryStream()` 的实现（构造带前缀的请求），下游拼接逻辑完全复用。
因此将来引入 B 不需要改动编码器与 pump —— 这是当前实现的收益。

## 6. 现状：A 方案（已实现，两个实现逐字节一致）

- 重试闸门从 `!hasEmittedContent`（任何内容，含 thinking）放宽为
  `canSpliceRetry`（仅正文/工具调用）：
  - 生产日志 77 次非取消类流内失败中，75 次（97%）是"thinking 已发、正文未发"
    的形状，旧闸门全部拒绝 → 这正是无人值守中断的根因。
- 续接时抑制重放的 thinking 与 role chunk，且**不重发 `message_start`**
  （实测：重发会让 Anthropic 客户端丢掉整条消息）。
- 定案依据：`conformance/client-probes/retry-splice.mjs`（两个真实 SDK × 5 种拼接
  方式）。结论：只有"原地续接 + 抑制重放"能让两个 SDK 都拿到完整答案且正文不重复。
- 契约固化：`conformance/scenarios/upstream-scenarios.json` 的
  `error-after-reasoning-recovered`（应重试）与 `error-after-text-no-retry`
  （不应重试），两侧实现输出逐字节一致。

## 7. 计费不隐瞒（与 A 方案配套）

每次上游尝试各落一行台账（`billing` 表），因为每次尝试都可能计费：

- 5xx/429 重试、模型发现重试、断流续接重试 **全部**单独记行，`attempt` 递增；
- 用量确实拿不到时存 **NULL**，绝不填 0（0 会把「未知」说成「零消耗」）；
- 中断的尝试标 `status='interrupted'`，字段含义见 `src/billing.ts`。
