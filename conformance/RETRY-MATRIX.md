# 重试决策矩阵

什么情况下会重试、什么情况下**该**重试——这是两个不同的问题，混在一起就会得出
"改了也没用"的修复（本项目在 `a3864f6` 上正是这样栽过一次）。

- **能不能**（can）：系统的机制限制。客户端/代理/SDK 里写死的分类逻辑，改文案或
  改错误类型都不影响它。
- **该不该**（should）：语义判断。同一个机制上完全可行，但重试是错的——因为重试
  不会得到不同结果，或会产生副作用。

所有"能不能"的格子都有实测来源；"该不该"来自语义推理 + 生产日志，**标注为判断而非
事实**。

---

## 2×2 矩阵

| | **该重试**（transient） | **不该重试**（permanent） |
| --- | --- | --- |
| **能重试** | ✅ **A 类** 正常恢复路径<br>· 建连失败 / DNS 失败<br>· 连接中途 reset（`terminated`）<br>· 上游 5xx（500/502/503）<br>· 上游 429 + `Retry-After`<br>· 请求阶段超时（未收到任何响应）<br>· **流内错误且未下发正文**（含仅 thinking，代理侧重试 ← 2026-09-15 新增） | ⚠️ **B 类** 危险区：机制允许但语义错误<br>· **已下发正文/工具调用后**的任何失败<br>· 4xx 语义错误（400/401/403/404）<br>· 配额耗尽类 429 |
| **不能重试** | ❌ **C 类** 想救但救不了<br>· 流内错误且**已下发正文或工具调用**（约 2/77）<br>— 曾包含"仅 thinking 已发"，现已移入 A 类 | ✅ **D 类** 本来就该放弃<br>· 本地校验失败（400，没发出请求）<br>· 客户端主动取消<br>· 认证失败<br>· 模型不存在<br>· 上下文超长 |

---

## A 类：能且该重试

**机制依据**（实测，`retry-classification.mjs`）：

| 形状 | 上游被请求次数（`maxRetries:3`） |
| ---- | -------------------------------- |
| HTTP 529 + `overloaded_error` | 4（重试了） |
| HTTP 500 | 4（重试了） |
| HTTP 429 | 4（重试了） |
| 200 + `error` 作为**首个**事件 | 4（重试了） |

生产日志印证：跨 3 天 `canRetry:true` 共 **179 条**，全部集中在
`server_error`（113 sse + 11 http）、`network_error`（32）、`rate_limited`（21 http）。
attempt 一路递增到 10，说明重试链在生产上确实在工作。

**注意 429 的双面性**：HTTP 层的 429（`transport: http`）可重试并确实重试了；
但流式路径的 429 若被判成 `provider_business` 就不能重试（见 C 类）。
同一个状态码，走哪条路径决定它落在哪个格子。

**代理内部（L1 层）的重试**与这里一致：`src/upstream.ts:168` 只对
`status >= 500 || status === 429` 重试，`MAX_RETRIES = 2`，线性退避 500ms。
关键约束：**只在响应头到达前**。

## B 类：能重试但不该重试（危险区）

这一格是"机制上完全可行、但重试是错的"，也是最容易被误用的地方。

### B1 已推流后的任何失败（最重要）

一旦正文开始流向用户，重试意味着**用户会看到同一段话写两遍**。这是本项目
`a3864f6` 犯的错：它想通过改错误类型让下游重试，而下游即使重试了，语义也是错的。

但请注意 §2.4.3 的另一面：**`message_start` 之前**的错误，连"已推流"都算不上——
那才是应该重试的窗口。这正是"先探首块再决定状态码"这条路有价值的原因。

### B2 4xx 语义错误

| 状态码 | 重试的结果 | 为什么不该 |
| ------ | ---------- | ---------- |
| 400 | 同样的 400 | 请求本身有问题，重发不改结果 |
| 401 | 同样的 401 | 除非期间换了 key，否则无意义 |
| 403 | 同样的 403 | 权限/模型不存在，与时机无关 |
| 404 | 同样的 404 | 端点或资源不存在 |

实测确认这些**确实不会被重试**（`K-http-401` / `L-http-403` / `M-http-400`
都是 1 次请求）——所以这一格是"机制恰好与语义一致"，属于幸运的巧合，
而不是设计保证。若换了客户端实现，这一格可能滑到 B 类。

### B3 配额耗尽类 429

`429 Too Many Requests` 有两种含义，**必须区分**：

- **速率限制**（"你太快了"）→ 该重试，退避等待即可 → A 类
- **配额耗尽**（"你没钱了"）→ 不该重试，重试只是浪费时间和额度 → B 类

生产实测的那 7 条 429 全是 `user concurrency limit exceeded`，被判
`retryable:false`（`provider_business`）。**这个判定是正确的**，虽然它和
A 类里"429 可重试"看起来矛盾——区别在于判定发生在不同层。

## C 类：该重试但重试不了（本项目当前的核心问题）

| 形状 | 上游被请求次数 | 结论 |
| ---- | -------------- | ---- |
| 200 + `message_start` 后 `error` | **1** | 不重试 |
| 200 + 正文后 `error` | **1** | 不重试 |
| 200 + `error` 后补 `message_delta(end_turn)` + `message_stop` | **1**，且 `finishReason: "stop"` | 不重试，**且被伪装成正常结束** |
| 同上，但类型换成 `api_error` | **1** | 类型无关 |
| 同上，但类型换成 `rate_limit_error` | **1** | 类型无关 |

**根因**：AI SDK 只在**首块探测**阶段构造可重试的 `APICallError`；`message_start`
一旦处理过，`error` 就只是 `enqueue` 出来的一条流内记录，重试包装器只认
`APICallError.isRetryable === true`，永远看不到它。

**生产实证**：v0.4.2 已把流内错误标成 `overloaded_error`，2026-09-14 22:56 那次
仍是 `retryable:false` / `attempt 1/11`，整轮报废。修复部署了，问题没解决。

**唯一的出路**：代理**在发 `message_start` 之前先把上游首个事件探出来**。
若首个事件就是 `error`，改回真实状态码（502/529）——那就落回 A 类，可重试。
代价是缓冲首块 + 改时序契约。

### 已实施：把重试挪到代理侧（2026-09-15）

上面那条"探首块"的出路**没有采纳**。实际采用的方案不需要缓冲首块：

**下游客户端救不了，但代理可以自己重试——关键是把「已经向客户端写过什么」和
「能不能重试」分开。**

旧闸门是 `!hasEmittedContent`：thinking 一开块就翻转，于是"thinking 已发 7662 字符、
正文未发"这种事故形状被拒绝重试。生产日志里 77 次非取消类流内失败中，**75 次
（97%）正是这个形状** —— 旧闸门挡住了绝大多数本可挽救的请求。

判别标准改为**是否已下发正文或工具调用**（`canSpliceRetry`）：

| 已下发的 | 能否重试 | 理由 |
| -------- | -------- | ---- |
| 无 | 能 | 客户端什么都没看见 |
| 仅 thinking | **能** | 重放的 thinking 会被抑制，用户无感 |
| 正文 | 不能 | 用户会读到同一段话两遍（探针 E） |
| 工具调用 | 不能 | 会得到两个 tool_use（探针 F） |

**拼接方式必须是原地续接**，不是朴素重发整轮。实测（`retry-splice.mjs`，两个真实
SDK）：

| 拼法 | Anthropic 客户端结果 |
| ---- | -------------------- |
| 朴素重发整轮（重发 `message_start`） | `text=""`、`finish=error` —— **整条答案丢失** |
| 原地续接 + 保留第二轮思考 | 答案完整，思考写了两遍 |
| 原地续接 + 抑制重放 | **答案完整，思考只出现一次**（采用） |

因此编码器新增 `beginContinuation()`：不重开信封（不重发 `message_start`）、不重置
块索引、丢弃重放的 thinking 与 role chunk。惰性重试仍只有一次。

**C 类剩下的部分**：正文或工具调用已经下发后失败仍只能如实报错，这一格没有出路，
继续留在 C 类 —— 占比 2/77。

**回归契约**：`upstream-scenarios.json` 里的 `error-after-reasoning-recovered`
（应该重试）与 `error-after-text-no-retry`（不该重试），两个实现逐字节一致。

**为什么不改成"带前缀续写"（让上游只生成剩余部分）**：CC 协议不支持续写，只能把
半截内容塞进 `messages` 当 assistant turn，那是换了语义完全不同的请求（模型会重审
前半截，半截 tool_use 也不合法）。详见 `CONTINUATION-MEMO.md`。

## D 类：不能也不该重试（本来就该放弃）

- **本地校验失败**（400）：请求没发出上游，重试是纯浪费。
  代理侧对应 `validation.ts` 的 7 类拒绝。
- **客户端主动取消**：`reason: cancelled` → `retryable:false`。用户的意图就是停，
  重试是违背用户意图。
- **认证失败**（401/auth_failed）：跨 6 天日志里 9 条，全部 `retryable:false`。
- **模型不存在**（裸名 403）：代理有一层专门的"学习目录后重试一次"
  （`sendToCCWithModelDiscovery`），那是**发现重试**不是**错误重试**——
  只试一次，真不存在就放弃。
- **上下文超长**：重发同样的上下文只会再超一次。

## 落到实现上的检查清单

1. **别指望改错误类型能救流内失败**——类型完全不参与判定（C 类）。
2. **流内错误后不要补 `message_delta(end_turn)`**——会把断流洗成正常结束。
3. **重试要固定 `threadId`**——否则一次意图烧两个会话（已修，见
   `sendToCCWithModelDiscovery`）。
4. **区分"速率 429"与"配额 429"**——前者重试，后者放弃。
5. **重试闸门看的是"正文/工具调用"，不是"任何内容"**——thinking 已发仍可续接
   （重放被抑制）。这是 97% 流内失败的形状。
6. **续接必须原地，不能重发 `message_start`**——重发会让 Anthropic 客户端丢掉整条
   消息（探针 B vs D）。
7. **每次上游尝试都要落一行计费台账**——包括被放弃的尝试；用量未知时存 NULL 而不是 0
   （见 `src/billing.ts`）。
