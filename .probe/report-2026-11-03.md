## 三、问题清单（按严重度）

### P0-1 Linux 自动更新有三条彼此独立的死路

1. **格式不支持**。`archive::extract()` 只解 zip（`archive.rs:269` → `read()` → `eocd_offset`，用 `flate2::read::DeflateDecoder` 解 zip 条目）。Linux 资产是 `.tar.gz`，会直接报"不是有效的 zip（找不到目录尾记录）"。整个 `archive.rs` 没有 tar 解析、也没有 gzip 包装解码。
2. **目录结构对不上**。`update.rs:421-447` 要求解包后**根层**存在 `CCProxyTray`；而 `packaging/aur/build-tarball.sh` 产出的 tarball 是 FHS 树：
   ```
   ./usr/bin/commandcode-proxy
   ./usr/bin/commandcode-proxy-tray      ← 名字也不是 CCProxyTray
   ./usr/share/commandcode-proxy/webui/…
   ./usr/lib/systemd/system/…
   ```
   即使解压成功，也会在"更新包里没有托盘程序"处失败。
3. **安装根不可写、路径不成立**。`install_root()` 只认「父目录叫 `service/`」这一种布局。deb 把二进制装到 `/usr/bin/commandcode-proxy`，于是 `install_root() = /usr/bin`，`staged_root_for("0.7.8") = /usr/CCProxy-v0.7.8-rust`。而 systemd 单元是 `User=commandcode-proxy` + `ProtectSystem=strict` + `ReadWritePaths=/var/lib/commandcode-proxy /var/log/commandcode-proxy` —— `/usr` 只读、且无 root 权限。**这个"同级 A/B 目录"模型是 Windows 免安装 zip 的模型，deb/AppImage 上不成立。**

建议方向（待你给细节后再定）：Linux 侧把更新改成"检测 + 提示"，实际安装交给包管理器（`apt` / `pacman -Syu` / 替换 AppImage），不要自己写 `/usr`。

### P1-1 上游 200 + HTML 错误页 → 客户端拿到"成功的空回答"

复现：让上游对任何请求返回 `200 text/html` 的 `<html>…502 Bad Gateway…</html>`。

- 非流式：`HTTP 200` + `{"content":[{"type":"text","text":""}],"stop_reason":"end_turn",…}`
- 流式：`message_start` → `message_delta(end_turn)` → `message_stop`
- 账本：`status = ok`，`completionTokens = 1`

也就是说，中间代理/门户注入的 HTML 错误页会被**伪装成一次成功的空回复**。对一个人人都在用的本地代理来说，这比报错更难排查。同类的 `garbage` 模式（全是无法解析的 `data:` 行）也是同样结果。

根因是流结束时没有"至少解析到一个有效事件"的校验，直接落到 `billing::Status::Ok`。`silent` / `gap` / `error_event` 都能正确标记错误，只有"有 HTTP 200 且持续有字节但内容无法解析"这一条漏了。

### P1-2 dev 分支版本号落后于已发布版本，会触发"伪更新"

- 当前 `Cargo.toml` → `0.7.7`；最新 release → `v0.7.8`（`v0.7.8` 打的那个提交里 Cargo 版本确实是 0.7.8）。
- `v0.7.8` **不是** `feat/ux` 的祖先。
- 后果：从本分支构建运行的实例会一直显示"有更新 0.7.8"，用户一点"安装"，就会用**不含果冻主题等新工作的旧发布版**覆盖掉本地构建。

建议：本分支合并前先把 workspace 版本推到 `0.7.9`（或明确 dev 构建不参与更新检查）。

### P2-1 CLI 参数解析：`--port` 单独用会报错，`--help` 会启动服务

`main.rs:25-31` 用「第一个不以 `--` 开头的参数」当子命令：

| 命令 | 期望 | 实际 |
|---|---|---|
| `ccproxy --port 8803` | 用该端口启动（代码注释明确写了这个用法要保留） | `ERROR unknown command "8803"` |
| `ccproxy --help` / `--version` | 打印帮助/版本 | 无输出，**当作 `start`**，去绑 8787（实测报 bind 失败） |
| `ccproxy start --port 8807` | 正常启动 | 正常 |

在 Linux 上尤其容易踩：运维在终端敲 `commandcode-proxy --help`，得到的是一个正在后台监听的进程（如果 8787 空闲）。

### P2-2 `stop` 的失败被吞掉，控制台中文乱码

- 目标进程已不存在时，`taskkill` 报错，但命令仍打印"stopped"并 `exit 0`。
- zh-CN Windows 下 `taskkill` 的中文输出被原样透传到 UTF-8 控制台，显示为 `�ɹ�: ����ֹ PID …`。

### P3-1 deb 没有 `prerm` / `postrm`

`apt purge` 之后 `/var/lib/commandcode-proxy`、`/var/log/commandcode-proxy`、`/etc/commandcode-proxy`、以及 `commandcode-proxy` 系统账号都会留下。postinst 建了账号和目录，但没有对应的清理。

### P3-2 不带 env 手跑 deb 版时面板 404

`config::webui_site_dir()` 只认 `CC_WEBUI_DIR` 或「exe 同目录 `webui/`」。deb 把面板放在 `/usr/share/commandcode-proxy/webui`，靠 systemd 单元注入环境变量。所以 `systemctl start` 正常，**手工 `commandcode-proxy start` 则面板 404**。

### 观察项

Linux 代码路径在本机无法编译验证：只装了 `x86_64-pc-windows-gnu` 与 `x86_64-unknown-linux-musl`，缺 `x86_64-linux-musl-gcc`，`cargo check --target x86_64-unknown-linux-musl -p ccproxy-tray` 在 `cc-rs` 处失败。Linux 编译正确性目前**只有 CI 一条防线**。
